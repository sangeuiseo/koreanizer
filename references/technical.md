# 기술 문서 모드

글이 API 문서, 설계 문서, 장애 보고서, 릴리스 노트, PR 설명, 커밋 메시지, 코드 주석이거나 코드가 섞여 있으면 이 파일을 읽는다. SKILL.md의 규칙을 대체하지 않고 그 위에 얹는다. `N절`은 SKILL.md의 패턴 번호다.

읽는 방식이 다르다. 기술 문서는 처음부터 끝까지 읽지 않고 필요한 줄을 찾아 읽는다. 매끄러운 것보다 찾기 쉬운 것이 앞선다.

사실을 한 줄씩 놓은 문장이 이어져도 31절로 보지 않는다. "이 API는 동기다. 호출은 블로킹된다. 타임아웃은 30초다"는 극적 효과가 아니라 참조용 배치다. 이어 붙이면 독자가 필요한 한 줄을 집어내지 못한다. 문장도 3절이 감시하는 `~하며` 연결로 밀려난다.

조건과 순서는 목록으로 푼다. 조건이 셋을 넘으면 한 문장에 담지 않는다. 여기서 문단을 쪼개는 것은 원문 훼손이 아니다.

명령, 설정값, 경로는 코드 블록에 그대로 둔다. 복사해서 쓰는 것이므로 산문으로 풀지 않는다.

낯선 이름은 처음 나올 때 무엇인지 드러나게 놓는다. 이름을 쉬운 말로 바꾸는 것이 아니라 그 이름이 무엇을 정하는지 문장이 말하게 하는 것이다. "`checkYn` 필드가 `Y`면 성인 인증 화면을 띄운다"보다 "성인 인증 화면을 띄울지는 `checkYn` 필드가 정한다. `Y`면 띄운다"가 읽기 쉽다. 이름은 양쪽 다 살아 있다.

PR 설명과 커밋 메시지는 무엇을 왜 바꿨는지가 본문이다. 바꾼 파일을 나열해 분량을 채우지 않는다. `-했음`, `-함` 같은 명사형 종결을 그 팀이 쓰면 남긴다. 11절의 종결 반복으로 보지 않는다.

코드 주석은 지금 코드가 무엇을 하는지 말한다. 30절이 여기 걸린다. 왜 이렇게 했는지는 코드가 못 말하므로 주석에 남긴다.

기호가 서술어 자리를 차지한 곳을 푼다. 조사가 문법 역할을 표시하므로 기호가 그 자리를 먹으면 독자가 관계를 추론해야 한다. `성능·안정성 개선`은 둘이 나란한지 앞이 뒤를 꾸미는지 말하지 않는다. `캐시/세션 정리`는 "와"인지 "또는"인지 말하지 않는다. `요청 실패 → 재시도`는 차례인지 까닭인지 말하지 않는다. 괄호가 열다섯 자 넘는 절을 삼킨 자리도 같다. "성능과 안정성을 개선했다", "캐시와 세션을 지운다", "요청이 실패하면 다시 시도한다"처럼 조사와 서술어를 되살린다.

제목과 이름표는 그대로 둔다. 중점으로 이은 제목은 그 장르에서 오래 쓴 형태다. 관계를 원문으로 알 수 없으면 고르거나 이어 붙이지 않는다.

원문에서 알 수 있는 것만 드러낸다. 그 이름이 무엇인지 원문에 없으면 지어내지 않고 묻는다.
